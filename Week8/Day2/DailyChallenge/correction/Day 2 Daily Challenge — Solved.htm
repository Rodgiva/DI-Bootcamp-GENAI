If you get version conflicts

Restart the runtime (Runtime → Restart session), then run this cell again. Colab pre-loads some of these packages, and pip cannot replace a module that is already imported.

After ANY restart: NameError: name ’pc’ is not defined

This is the error you are most likely to hit today, and it is not a bug in your code. A runtime restart erases every variable — pc, query, documents, index, all of them. It erases environment variables too, so the key set by Authenticate() is gone with them.

The trap is that the restart is something the warning above told you to do. You restart to clear a pip conflict, carry on from the cell you had reached, and the next cell fails naming a variable you are certain you created.

The fix is never to re-run one cell. Use Runtime → Run all, or right-click the cell you are on and choose Run before. You need the habit anyway: “restart and run all” is exactly the check your submission has to pass.

How to tell a restart happened: the traceback path carries a kernel number — /tmp/ipykernel_2271/…. If that number changed since your last error, you are in a new runtime and nothing from before survives.

Set a Colab Secret once and stop re-authenticating

The Authenticate() panel re-prompts on every fresh runtime, and you will restart more than once today. A Colab Secret survives restarts and is never saved into the notebook.

import os, time
import pandas as pd
from pinecone import Pinecone, ServerlessSpec
from transformers import AutoTokenizer, AutoModel
import torch

cloud  = os.getenv('PINECONE_CLOUD',  'aws')
region = os.getenv('PINECONE_REGION', 'us-east-1')
spec   = ServerlessSpec(cloud=cloud, region=region)

index_name = 'medical-notes-index'

if pc.has_index(name=index_name):      # makes the cell safe to re-run
    pc.delete_index(name=index_name)

pc.create_index(
    name=index_name,
    dimension=384,                     # must match the vectors in the data file
    metric='cosine',
    spec=spec,
)
print("created:", index_name)
What the code does
  1. dimension=384 — this is not a preference, it is a fact about the data. The vectors in the file are 384 numbers long because they came from all-MiniLM-L6-v2. Any other number and every upsert fails.
  2. metric='cosine' — compares the direction of two vectors and ignores their length, which is what you want for text.
  3. has_index then delete_index — the challenge includes this so the cell can be re-run. It also means a careless re-run silently destroys an index you wanted. Fine here; dangerous habit elsewhere.
  4. aws / us-east-1 — the free-tier defaults. The os.getenv wrapper lets you override them without editing code.
What you should see
created: medical-notes-index
Dimension mismatch is the error you are most likely to hit

If an upsert fails with a dimension error, you created the index with the wrong number. You cannot change the dimension of an existing index — delete it and create it again at 384.

Why this step exists

A serverless index is the managed version of the FAISS index you built by hand: same job, somebody else's machine, and a bill. The parameters you are filling in are the three it cannot guess — how long your vectors are, how to compare them, and where to run.

Embed the question — and mind the pooling dimension

What the challenge asks

💡 Hint: we want to average across the sequence length dimension to get a single vector per input.

Part 5.2: write a medical question and choose how many results to retrieve.

Turn the question into a vector and search
def get_embedding(input_question):
    model_name = 'sentence-transformers/all-MiniLM-L6-v2'
    tokenizer = AutoTokenizer.from_pretrained(model_name)
    model = AutoModel.from_pretrained(model_name)

    encoded_input = tokenizer(input_question, padding=True,
                              truncation=True, return_tensors='pt')
    with torch.no_grad():
        model_output = model(**encoded_input)

    embedding = model_output.last_hidden_state[0].mean(dim=0)   # <- 0
    return embedding

question = "what if my patient has leg pain"
query = get_embedding(question).tolist()

results = index.query(vector=[query], top_k=10, include_metadata=True)
sorted_matches = sorted(results['matches'], key=lambda x: x['score'], reverse=True)
print(len(sorted_matches), "matches")
What the code does
  1. last_hidden_state is (batch, seq_len, 384). The [0] takes the first sentence, leaving (seq_len, 384) — so sequence length is now dimension 0.
  2. .mean(dim=0) — averages across the tokens and gives one 384-number vector for the whole sentence. That is mean pooling, and it is how MiniLM is meant to be used.
  3. top_k=10 — ten candidates. Deliberately more than you want, because the reranker needs something to reorder.
  4. include_metadata=True — without it you get ids and scores only, and Part 6 has nothing to rerank.
What you should see
10 matches
Why dim=0 and not dim=1 — I checked the shapes
last_hidden_state  (1, 12, 384)   batch, tokens, dims
after [0]             (12, 384)   tokens, dims

.mean(dim=0)             (384,)   one vector per sentence   CORRECT
.mean(dim=1)              (12,)   one number per token      WRONG

dim=1 does not raise an error. It returns a 12-number vector, your upsert dimension check passes nothing, and the query fails later with a dimension mismatch that points at the wrong line.

One real flaw in this function, worth a line in your write-up

padding=True is set, but the mean ignores the attention mask — so if you ever pass a list of questions, the padding tokens get averaged in and every vector is slightly wrong.

Here it is harmless, because one string means no padding. Proper mean pooling multiplies by the attention mask first, which is exactly what SentenceTransformer does for you. Reaching for AutoModel means doing that yourself, and this skeleton does not.

Also: the function reloads the model on every call. Move those two lines outside and it runs in a fraction of the time.

Why this step exists

Note what is being embedded: only the question. The 100 notes were embedded by somebody else and shipped in the file. That asymmetry is the economics of every search system — documents once, questions forever.

Reranking does not always change the order, and a notebook showing “no change” with an honest explanation is worth more than one that pretends otherwise.

When it does happen, try a refined query that pulls harder away from the original — search for something broad like ‘patient has pain’, rerank for something narrow like ‘patient needs knee surgery’. The wider the gap between the two, the more there is for the reranker to do.

The sentence that answers “why bother?”

Search compares two vectors. Reranking reads the question and the document together.

The note's vector was made before anyone asked anything, so it is a summary of the note and nothing else. The reranker sees the actual question and the actual text at the same time, which is why it can tell knee surgery from leg pain — and why it is far too slow to run over all 100 notes.

So: cheap model narrows 100 to 10, expensive model sorts those 10. That two-stage shape is the standard way production search is built, and it is the same thing you did by hand in Day 2's Step 15 with a local cross-encoder. This challenge is that lesson again, as somebody else's API.

Why this step exists

Notice the query changed too: you searched for leg pain and reranked for knee surgery. That is deliberate in the skeleton — cast a wide net with the cheap model, then narrow it with the expensive one.
